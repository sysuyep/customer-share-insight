# 阶段 3：逐页框架

逐页框架是整套分享的施工图。页面之间跳跃、讲述句被放上页面、数字重复、模块混在一起——这些问题在这一步改只要几分钟，等页面做出来再改要几个小时。所以这一步要写到每一页，并且做完自查再交给用户。

## 目录

1. 每页要写的字段
2. 标题连读和自查
3. 常见问题和改法
4. 在企业微信等渠道里分条发送
5. 结束时怎么问

---

## 1. 每页要写的字段

```markdown
## P# · [页面标题]

- 所属模块：[模块展示标题]
- 页面作用：[见下表]
- 页面主张：[一句完整的话；观点页能在前面加"我认为"读通]
- 承接上一页：[上一页留下了什么问题，这一页怎么接]
- 引出下一页：[这一页结束时留下什么，让下一页自然出现]
- 上屏文字：[页面上出现的全部文字：标题、副标题、说明、图示里的字]
- 讲稿要点：[分享人现场补充的背景、过程、感受，不上屏]
- 依据：[原文位置 / 事实 / 数据 / 推断]
- 版式：[deck-guide.md 里的版式名]
- 素材：[无 / Logo / 本人照片 / 现场照片 / 示意图 / 占位]
- 博商暗线：[只在这一页用到时写]
```

页面作用：

| 作用 | 用途 |
|---|---|
| 封面、画像、模块导览、模块过渡、收尾 | 结构页 |
| 观点、金句、场景 | 讲一个判断或一个瞬间 |
| 因果、对比、并列、矩阵、流程、层级、拆解 | 讲几件事之间的关系 |
| 数据 | 用大数字讲规模或变化 |
| 做法、决策原因、分阶段做法 | 讲"我们具体怎么做" |
| 结果 | 讲做了之后有什么变化 |

**上屏文字和讲稿要点一定要分开。** 判断方法：这句话是分享人站在台上对着听众说的吗？是，就放讲稿要点；页面上放的是提炼过的标题、短说明、数字和图示里的字。

| 讲稿要点（现场说） | 上屏文字（页面放） |
|---|---|
| 于是，我们把生产和运输放在一起做 | 生产和运输一起安排，让客户现场更快完工 |
| 那几年我天天在想，再这样下去公司撑不过两年 | 只靠一个区域，一场停工就能让公司停摆 |

## 2. 标题连读和自查

全部页面写完后，把标题按顺序列成一列：

```markdown
### 标题连读

P1 封面：[主标题]
P2 画像：……
P3 模块导览：……
P4 模块过渡：[模块 1 展示标题]
P5 ……
```

从头读一遍，像听众一样问：每一页为什么出现在这里？然后逐项自查，把结果写在标题连读下面：

- [ ] 封面和画像之后有一页模块导览；导览里的编号和模块标题，与各模块过渡页逐字一致。
- [ ] 标题连起来是一条通顺的思路，提出的问题都有回答，没有突然换话题。
- [ ] 相邻两页标题意思不同；同一个数字、同一个观点只出现一次。
- [ ] 每个模块有一页"我们怎么做"（做法、决策原因或分阶段做法）。
- [ ] 上屏文字里没有现场讲述句，没有"他""某某意识到"这类第三人称。
- [ ] 对客户做的事和公司内部管理没有混在一起。
- [ ] 版式和内容关系一致，没有"左边一段原话、右边几个标签"的页面。
- [ ] 画像页没有内部分析字段；缺素材的页面已规划占位。
- [ ] 页数和分享时长匹配。

发现问题就先改，再在自查结果里写明"发现了什么、怎么改的"，例如"P9 原本只提问题，已把 P10 的做法提前接上"。

## 3. 常见问题和改法

以下例子均为虚构，用来说明问题的样子。

### 例 1：左边一段原话，右边几个标签

```text
左：我们 2019 年开始转型，因为老渠道利润越来越薄，我跑了一年市场，
    发现新一代客户根本不通过老渠道买东西。
右：· 战略  · 转型  · 渠道  · 客户
```

右边的标签没有信息，也没有把左边推进一步。原话本身就是转折点，改成金句页：

```text
"新一代客户根本不通过老渠道买东西。"
下方一行：从那一年起，我决定拆掉延续了 12 年的代理体系。
```

### 例 2：三个并列点之间没有关系

```text
标题：我是怎么开始的
· 朋友一句话 → "我有个活儿，你来帮我做"
· 第一辆车   → 四个员工跟着我上了车
· 起点       → 不是规划出来的，是被逼出来的
```

三点不是时间顺序，也不是因果或对比：前两点是同一件事的两面，第三点是总结。先问这一页要让听众明白什么——"起点是被动的"——再选版式：

```text
大主张：我的起点不是规划出来的，是被一句话推出来的
下方说明：原来的生意一夜之间停了，朋友说"我有个活儿，你来帮我做"。
          第二天，我带着四个员工开着借来的车去了。
```

### 例 3：事实堆了一页，没有观点

```text
标题：一个项目，上千个细节
□ 一个项目要七个人做一天，不能拖到第二天
□ 做好了也有人挑，做不好更有人挑
□ 一天收入几千，但人手翻倍也做不到两倍
□ 赚到钱了，大家都很累
```

每条都是事实，听众不知道要明白什么。改成观点加证据：

```text
观点：做得越好越累——这不是勤奋的问题，是模式的问题
证据：一天的收入要七个人、一整天才能换来，人手翻倍也做不到两倍。
```

### 例 4：现场讲的话被放上页面

```text
标题：于是，我们决定自己买车
右下角小字：不是多卖一项服务，而是从生产到运输一起安排，让客户更快完工。
```

标题是现场讲述句，真正的观点反而缩在角落。改法：把角落那句提炼成标题，讲述句放进讲稿要点。

```text
标题：从生产到运输一起安排，让客户现场更快完工
说明：一车货的卸货时间从 40 分钟缩到 8 分钟
图示：生产 → 运输 → 卸货 的三段流程
```

### 例 5：两页之间跳跃

```text
P8 我们的能力是一层层长出来的
P9 让客户早点下班
```

P8 讲公司自己，P9 突然讲客户，中间缺一句"为什么"。补一个承接：在 P9 的标题前先回答"设备和能力都齐了，客户为什么还要选我们？"，或者把它写进 P9 的说明。

### 例 6：封面、模块导览页和模块过渡页

- 封面不放 01 这类序号，只放主标题、副标题、分享人和公司。
- 模块导览页全场只有一页，放在画像页之后，用 01、02、03 标出顺序。
- 模块过渡页在每个模块开头各一页，用大号编号加模块标题，让听众一眼看出"开始讲第几部分了"；编号和标题都与导览页逐字一致。可以加一句副标题或一句原话。
- 过渡页要足够醒目，不能只在页面角落放一个小目录。

编号本身不是问题，问题是把不相关的内容硬凑成 01、02、03。步骤、阶段、并列做法可以编号；内容之间没有顺序或并列关系时不要编号。

## 4. 在企业微信等渠道里分条发送

企业微信、微信、钉钉等渠道对单条消息有字数上限（常见约 2000–4000 字）。一次发完 20 页框架，代码块会在中间被截断，后面的页面跑到代码块外、格式全乱。

- 默认每个模块发一条消息：一行普通文字写"模块 2 · [展示标题]（P10–P14）"，然后一个开头和结尾都完整的 markdown 代码块，最后一行写"这是第 2 / 4 个模块，回复'继续'发下一个，有修改请直接告诉我"。
- 一个模块太长（单条估计超过 1800 字），再拆成两条，第二条开头写"模块 2 续（P13–P14）"。不要为了塞进一条而删字段或合并页面。
- 代码块必须开了就闭，不要发出只有开头或只有结尾的代码块。
- 能发文件的环境，可以把完整框架写成 `{customer}_{topic}_page_plan.md` 发给用户，对话里只发每个模块一行的摘要。
- 所有模块发完后，单独发一条标题连读和自查结果，再问是否进入阶段 4。

阶段 2 的三个方向太长时，同样一个方向一条消息。阶段 4 是把文件写到磁盘，不受这个限制，不要在阶段 4 分条在对话里发 HTML。

## 5. 结束时怎么问

> 逐页框架、标题连读和自查结果都在上面了。请您确认：① 每页的内容和顺序是否符合您的想法；② 有没有要删、要合并或要补的页面。确认后我先做视觉样稿给您挑，再做整套。
